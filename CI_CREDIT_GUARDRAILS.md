# BINDING OWNER POLICY — CI/CD Credit Conservation & Provider Fallbacks
Effective: 2026-11-18. Applies to ALL code agents, IDE assistants, chat assistants, human operators, and automated contributors. This is a portfolio-wide **mandatory** owner instruction. It is not a request to reduce actual product security or acceptance evidence.

## Default: spend ZERO hosted CI credits during ordinary iteration
- Before touching a CI workflow, inspect actual triggers, currently available credits and existing project-specific safety obligations.
- Do not push one-line debugging commits to trigger hosted checks. Edit, inspect, and run the smallest relevant equivalent validations locally or in already-provisioned compute first. Make coherent checkpoints.
- Never invoke GitHub Actions, CircleCI, Cloudflare Builds, Browser Run, external paid APIs, or an on-demand hosted runner merely for progress reporting, formatting, trivial docs, exploratory diagnostics, repeatability theater, or to re-run already evidenced unchanged tests. Do not add scheduled runs or synthetic credit-spending watchdogs.
- **Hosted test opt-in** requires a recorded reason: changed files, test-risk mapping, exact commit/tree, required checks, provider, available budget, expected total minutes/credits, owner authorization if a hard limit would be exceeded. No silent use of a substitute provider.
- Classify changes: (0) docs-only/copy and non-runtime metadata: no hosted test or deployment; (1) narrow UI/source: changed-path static contracts and focused browser/unit tests; (2) auth/privacy/D1/migrations/purchases/payments/deploy infrastructure: full affected security/integration gates, never skipped for cost; (3) release: independent, exact-revision acceptance and protected production smoke checks. A documented exception may ADD necessary tests, never suppress a safety gate.
- Do not run complete suites twice on the same exact code/tree/dependencies and comparable environment. Reuse recorded proof only if the verification receipt identifies all conditions (tree/commit, test commands and versions, configuration, checks, provider, result, freshness, source signature) and the promotion policy explicitly permits reuse. A changed tree, missing check, test failure, or ambiguous proof means it is **NOT verified**.
- A failing assertion is not a runner outage. Fail over to another provider only for demonstrated capacity/outage/infrastructure failure. A failure that cannot be reproduced locally is investigated, not declared green.
- Preserve required status checks, branch protection, independent external monitoring, protected secrets, backups, D1 compatibility, privacy/identity checks, rollback, and any project-specific regulation/security/commerce gates. Do not cut health-monitor frequency to save credits or move independent monitoring onto its own target host.
- Keep one protected deployment coordinator. Do not set Cloudflare Pages/Workers auto-production deployment or secondary deploy hooks in parallel with the existing orchestrator. Worker and Pages revisions must match when the project requires parity, and production readback is mandatory.
- Provider pools: local/self-hosted for iteration; Cloudflare Workers Builds for selective compatible build/static/Node/Python checks in an isolated CI-only Worker; GitHub Actions for manually approved full/browser release verification when appropriate; CircleCI as a reserve fallback until credits recover. **No provider is automatically a substitute** for a missing required check.
- Concurrency: cancel superseded read-only jobs; serialize stateful writes and deployments. Cache dependencies where safe. Keep recorded monthly budgets and run counts, with a hard **no-run** condition on insufficient quota or unavailable evidence.

## Every task must explicitly account for cost
An agent's closing report identifies checks run vs intentionally not run, exact reason, provider usage/cost estimate, remaining risk, commit/PR and release proof. **A merge is not a deployment.** If cloud checks cannot run, leave the release blocked and report that honestly.

## Hierarchy and application
This owner mandate supersedes older blanket "run full hosted CI on every push" habits. It does **not** supersede strict project-specific security requirements or justify removing a required gate. Read the project's own `AGENTS.md`, CI/runbook and [portfolio policy](https://github.com/m7mdehab/ai-engineering-control-plane/blob/main/CI_EFFICIENCY_POLICY.md). A project's distinct CI mechanism and external monitoring are preserved until specifically reviewed and migrated. When multiple instructions conflict on cost, the stricter *conservation* rule wins; on correctness/security, the stricter *verification* rule wins.
